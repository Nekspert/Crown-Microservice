# Микросервис трекинга статуса тендеров

Backend-приложение для создания тендеров, управления их статусом
(Черновик → Активен → Выигран / Проигран) и логирования **каждого** изменения статуса:
кто изменил, когда и почему - в отдельную таблицу истории (`tender_history`).

---

## Логика решения и алгоритм

### Постановка задачи

Сервис управляет жизненным циклом тендера. Тендер создаётся в статусе **Черновик**,
может перейти в **Активен**, а затем - в **Выигран** или **Проигран**.
Каждое изменение статуса обязательно фиксируется в отдельной таблице истории:
**кто** изменил, **когда** и **почему**.

### Алгоритм работы

1. **Создание тендера** - клиент отправляет `POST /api/v1/tender` с заголовком и описанием.
   - Слой `application` создаёт доменную сущность со статусом `Черновик`.
   - Слой `infrastructure` сохраняет тендер в PostgreSQL.
   - Ответ: `201` с данными созданного тендера.
2. **Изменение статуса** - клиент отправляет `PATCH /api/v1/tender/{id}/status`
   с новым статусом, причиной и `changed_by`.
   - Слой `domain` проверяет переход по **машине состояний**:
     `Черновик → Активен → Выигран / Проигран`; обратные переходы и «перескоки» запрещены (`400`).
   - Слой `application` создаёт запись истории: `old_status`, `new_status`,
     `changed_by`, `changed_at`, `reason`.
   - **Статус и история сохраняются в одной транзакции** - данные всегда согласованы.
3. **Чтение** - `GET /api/v1/tender/{id}` возвращает текущий тендер,
   `GET /api/v1/tender/{id}/history` - всю историю изменений.

**Реализует задания:**
- **Задание 6: Микросервис трекинга статуса тендеров**
  - Backend-приложение на Python (FastAPI). Сервис должен иметь эндпоинты для создания тендера, обновления его статуса (Черновик, Активен, Выигран, Проигран) и логировать каждое изменение статуса (кто изменил, когда и почему) в отдельную таблицу истории.
- **Задание 9: Развертывание и CI/CD (Docker-скрипт)**
  - Упаковать сервис в Docker-контейнер, настроить docker-compose.yml, который поднимает сразу три контейнера: само приложение (FastAPI), базу данных (PostgreSQL) и брокер очередей (Redis). Написать простой скрипт для GitHub Actions, который проверяет код линтерами (black, flake8) при каждом пуше.

## Архитектура

Проект построен по **чистой архитектуре** и разделён на четыре слоя.
Зависимости направлены строго внутрь: `presentation → infrastructure → application → domain`.


### Поток обработки запроса

1. **Presentation:** FastAPI-роутер принимает запрос, Pydantic-схема валидирует тело.
2. **Application:** use-case вызывается через dependency injection и манипулирует **domain**-сущностями.
3. **Domain:** проверяет допустимость перехода и применяет новое состояние.
4. **Application:** создаёт запись истории изменения.
5. **Infrastructure:** адаптер сохраняет тендер и историю в PostgreSQL.

## Быстрый старт

### Скачивание проекта

```bash
# Через HTTPS
git clone https://github.com/Nekspert/crown_microservice.git
cd crown_microservice

# или через SSH
git clone git@github.com:Nekspert/crown_microservice.git
cd crown_microservice
```

### Запуск без Docker

> ⚠️ При локальном запуске приложение на старте подключается к **PostgreSQL** и **Redis**,
> поэтому сначала нужно установить и запустить оба сервиса.

```bash
# 1. Установите зависимости (создаст виртуальное окружение и установит все библиотеки)
poetry install

# 2. Активируйте виртуальное окружение
poetry shell

# 3. Подготовьте переменные окружения
cp .env.example .env
# → отредактируйте .env под свои PostgreSQL/Redis (host/port/user/password/db)

# 4. Примените миграции (создаст таблицы tenders и tender_history)
alembic -c app/alembic.ini upgrade head

# 5. Запустите сервер
python -m app.run
```

Либо без `poetry shell` - всё одной строкой:

```bash
poetry run alembic -c app/alembic.ini upgrade head
poetry run python -m app.run
```

После запуска документация доступна по адресу **http://localhost:8000/docs** (Swagger UI)
или **http://localhost:8000/redoc**.


### Запуск в Docker

```bash
# Сборка и запуск всех трёх сервисов (app + PostgreSQL + Redis)
docker compose up --build -d
```

Команда поднимет:

| Сервис  | Образ                        | Порты          | Задача                          |
|---------|------------------------------|----------------|---------------------------------|
| `crown` | сборка из `Dockerfile`       | `8000:8000`    | FastAPI-приложение              |
| `db`    | `postgres:17.5-alpine`       | `5432:5432`    | PostgreSQL (проходит healthcheck) |
| `redis` | `redis:8-alpine`             | `6379:6379`    | Брокер очередей (Redis)         |

Приложение ждёт готовности `db` и `redis` (healthcheck), затем **автоматически применяет
миграции** (`alembic upgrade head`) и только после этого запускает сервер.

## API-эндпоинты

Все маршруты доступны под префиксом **`/api/v1`**. Интерактивная документация - `/docs`.

| Метод | Путь                                   | Назначение                             | Код успеха |
|-------|----------------------------------------|----------------------------------------|------------|
| POST  | `/api/v1/tender`                       | Создать тендер (статус = Черновик)     | `201`      |
| PATCH | `/api/v1/tender/{tender_id}/status`    | Изменить статус тендера                | `200`      |
| GET   | `/api/v1/tender/{tender_id}`           | Получить тендер по id                  | `200`      |
| GET   | `/api/v1/tender/{tender_id}/history`   | Получить историю изменений статуса     | `200`      |

Ошибки: **`404`** - тендер не найден, **`400`** - недопустимый переход статуса.

## Бизнес-логика и машина состояний

Статусы тендера заданы перечислением `TenderStatus` (`app/domain/tender/enums.py`):

| Значение  | Отображаемое имя |
|-----------|------------------|
| `DRAFT`   | Черновик         |
| `ACTIVE`  | Активен          |
| `WON`     | Выигран          |
| `LOST`    | Проигран         |

**Машина состояний** (`allowed_transitions` в `TenderEntity`):

```
Черновик ──► Активен ──► Выигран
                │
                └────────► Проигран
```

Допустимые переходы:

- ✅ `Черновик` → `Активен`
- ✅ `Активен` → `Выигран` / `Проигран`
- ❌ `Выигран` / `Проигран` → никуда (терминальные состояния)
- ❌ Обратные переходы и «перескоки» отклоняются ошибкой `400`

Дополнительные бизнес-правила реализованы в слое **domain** (валидация в `TenderEntity.__post_init__`):
идентификаторы должны быть положительными, заголовок - непустым, временные метки -
timezone-aware и не из будущего. Слой `application` получает уже валидную сущность
и не смешивает бизнес-правила с деталями БД.

## Логирование истории

Каждое изменение статуса сохраняется в отдельную таблицу **`tender_history`** через
use-case `ChangeTenderStatusUseCase`. Что фиксируется:

- **кто** - `changed_by` (идентификатор пользователя, переданный в запросе),
- **когда** - `changed_at` (UTC timestamp),
- **почему** - `reason` (обоснование из запроса),
- **что было / стало** - `old_status`, `new_status`.

Запись истории создаётся в **той же транзакции**, что и обновление тендера, поэтому данные
всегда согласованы: невозможно обновить статус без записи в историю. Прочитать историю
можно через эндпоинт `GET /api/v1/tender/{id}/history`.

## CI/CD

В `.github/workflows/ci.yml` настроен **GitHub Actions** workflow:

- **Триггеры:** `push` (в любую ветку).
- **Шаги:**
  1. `actions/checkout@v4` - получение кода,
  2. `actions/setup-python@v5` (Python 3.12) - окружение,
  3. установка Poetry и dev-зависимостей (`poetry install --only dev`),
  4. `black --check app` - проверка форматирования,
     `flake8 app` - проверка стиля (конфиг `.flake8`, max-line-length 88).
